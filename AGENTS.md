# FileManager — сведения для агентов

## Сборка и проверка

```powershell
cargo build            # dev-сборка
cargo build --release  # релизный exe → target\release\filemanager.exe
cargo test             # unit-тесты core
```

Перед релизной сборкой убедиться, что `filemanager.exe` не запущен
(иначе линкер упадёт с `os error 5`).

## Структура

- `src/core` — логика ФС, история, настройки, i18n, форматирование. Без egui и Win32.
- `src/platform/windows` — Win32-специфика (single instance, диски, локальное время).
- `src/ui` — виджеты egui (app, list, tree, props, tabs). UI только вызывает core/platform.

## Соглашения

- **Сообщения коммитов — на русском языке.**
- **Коммит = заголовок + описание того, что сделано** (описание попадает в changelog релиза).
- **Тело коммита — маркированный список** (`- пункт` на строку), чтобы в релизе это отображалось списком, а не сплошным текстом.
- **Стиль описаний — безличный, о самом изменении**, в тон changelog релиза: «Добавлено…», «Исправлено…», «Сохранена логика…». Первое лицо запрещено (см. раздел ниже).
- egui/eframe 0.37: `App::ui(&mut Ui, &mut Frame)`, панели — `egui::Panel::top/bottom/left/right(id)`.
- Строки интерфейса — только через `i18n/*.json` + `t("key")`, без хардкода.
- Выполненные пункты в `ROADMAP.md` помечаются `✅`.
- Токены/секреты не коммитить; локальные хуки живут в `.git/hooks` (не версионируются).
- В новых ветках не должно быть цифр в названии, только осмысленные названия отображающие суть изменений.
- Если есть ветка подходящая для нового изменения, сначала её обновить чтобы соответствовала ветке main, а только потом вносить изменения.
- При повышении версии приложения, названия комитов писать осмысленно и понятно, например: Версия 0.9.1.

## Сообщения коммитов и описания PR: формат и стиль

Changelog релиза собирается из сообщений коммитов, поэтому каждый коммит и каждый PR читает человек, который не видит код и не видит задач. Текст обязан быть понятен без контекста и описывать изменение, а не работу исполнителя.

### Главный принцип: безлично и о сути
- Писать не от лица разработчика, а об изменении в продукте и коде. Первое лицо запрещено везде: в заголовках, пунктах тела, описании PR («Добавил…», «Сохранил…», «Я проверил…»). Читателю changelog не важно, кто и какие усилия приложил; важно, что теперь работает иначе.
- Формулировки — страдательные краткие причастия или существительные, как в changelog релиза: «Добавлено внутреннее перетаскивание файлов», «Исправлено контекстное меню пустого места», «Сохранена логика marquee», «Добавлены тесты пустой папки».
- Каждый пункт говорит конкретную суть изменения поведения или кода, а не называет действие исполнителя. Плохо: «Сохранил прямоугольник фона по доступной видимой области панели» — читателю без диффа непонятно, что это меняет. Хорошо: «Фоновый отклик списка создаётся до отрисовки содержимого и покрывает видимую область панели».
- Запрещены также инфинитив («Стабилизировать…», «Сворачивать…») и именительные предложения без глагола («Нейтральный таб-бар…», «Подсказка следует за курсором»): заголовок и пункты констатируют факт изменения.

### Заголовок
- Одна строка, безлично: «Исправлено контекстное меню пустого места списка», «Добавлены сворачиваемые секции закладок», «Уточнена граница данных при сбросе».
- Коммит версии оформляется только как «Версия 0.9.1»; другие формулировки («Обновление 0.9.1») запрещены.
- Заголовок не дублирует тело, тело не повторяет заголовок дословно.

### Тело
- Маркированный список результатов: что изменилось в поведении или коде, что сохранено прежним, что покрыто тестами. Пункты безличные, в настоящем времени о новом состоянии («фон регистрируется после заглушки») или страдательным причастием о факте изменения («добавлены 10 тестов»).
- Пункты идут подряд, без пустых строк между ними: пустая строка разрывает список в changelog.
- Запрещены заголовки разделов внутри сообщения (`###`, `===`) и буквальные `\n` внутри строк. Пункт, в котором появился `\n` или вклеился кусок соседнего пункта, — ошибка сборки сообщения, а не особенность changelog.
- Каждый пункт самодостаточен и относится только к этому коммиту: запрещены фрагменты заголовков и тел других коммитов.
- Объём: 3–6 пунктов. Не пересказывать diff по файлам и не добавлять воду.

### Описание PR
- Те же правила стиля, что для коммита: безлично, о сути изменения. Разделы «Причина», «Изменения», «Проверки» допустимы, но пункты внутри них подчиняются правилам тела коммита.
- Описание объясняет читателю без диффа три вещи: почему было сломано или чего не хватало (одно-два предложения о причине в коде, а не о симптоме), что теперь работает иначе, какими проверками это подтверждено.
- Запрещён пересказ собственного процесса («я проверил», «я решил упростить», «я не трогал»): формулировать как факты о коде («логика marquee и DnD не изменена», «проверки прошли в debug и release»).
- Ручные проверки, которые не выполнялись, перечисляются отдельным списком со пометкой «не выполнено»; запрещается выдавать их за пройденные.

### Сборка сообщения без порчи
- Писать сообщение в файл и коммитить через `git commit -F <файл>`: это исключает shell quoting и буквальные `\n`.
- Либо по одному `-m` на абзац: первый `-m` — заголовок, каждый следующий `-m` — один пункт тела.
- Запрещено собирать тело одной кавычкой со встроенными `\n`.
- После коммита проверить себя: `git log -1 --pretty=%B`. Ожидание: пункты на отдельных строках, без `\n`, без чужих фрагментов, без пустых строк между пунктами, без первого лица.
- Если сообщение испорчено и коммит ещё не отправлен — поправить локально (amend допустим только до push). Если отправлен — историю не переписывать: правильное описание дать в теле PR, а факт косметического дефекта отметить в отчёте.

### Примеры

Хорошо:

```
Исправлено контекстное меню пустого места списка

- Фоновый отклик списка создаётся до отрисовки содержимого и покрывает видимую область панели
- В пустой папке фон регистрируется после заглушки, поэтому правый клик снова открывает меню
- Логика marquee, DnD и контекстных меню строк сохранена прежней
- Добавлены тесты пустой папки, нулевых результатов поиска и регистрации цели Background
```

Плохо (не повторять):

```
Исправил контекстное меню пустого места списка

- Сохранил прямоугольник фона по доступной видимой области панели до отрисовки содержимого
- Для пустого состояния зарегистрировал тот же отклик после заглушки; для непустого — до строк
- Добавил 10 детерминированных тестов для пустой папки, загрузки, нулевых результатов, кликов, marquee, Background и режимов
```

Ошибки: первое лицо в заголовке и во всех пунктах; пункты описывают действия исполнителя и внутреннюю кухню вместо сути изменения; последний пункт — перечисление усилий, а не факта покрытия.

```
Стабилизировать структурную проверку Tab DnD

- Нормализовать пробелы в исходнике перед проверкой общего флага payload

- Проверить передачу этого флага
```

Ошибки: инфинитив в заголовке и пунктах, пустая строка между пунктами.

## Git-гигиена

- Не запускать `cargo fmt --all`: в репозитории известные legacy-расхождения форматирования, массовый fmt создаёт посторонний diff. Форматировать только файлы своей задачи.
- Не выполнять force-push, rebase, amend и squash по уже отправленным коммитам.
- Агент открывает PR, но не сливает его: решение о слиянии принимает пользователь.
- Не смешивать задачи: одна ветка и один PR — одно изменение; посторонние правки в diff запрещены.
