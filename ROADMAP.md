# Дорожная карта проводника на Rust до версии 1.0

## 1. Общая цель

Создать вспомогательный файловый менеджер для Windows 11 x64, который:

- запускается как обычный `.exe`;
- работает рядом со стандартным Проводником Windows;
- имеет современный и быстрый собственный интерфейс на Rust;
- поддерживает основные функции проводника, необходимые для ежедневной работы;
- может использоваться другими пользователями;
- распространяется как portable-приложение;
- поддерживает автообновление;
- имеет русскую и английскую локализацию;
- поддерживает удаление в стандартную Корзину Windows;
- имеет отдельную защищённую корзину приложения;
- в будущем может быть расширен до полноценной замены стандартного Explorer, но без включения этой задачи в версию 1.0.

---

## 2. Что считается версией 1.0

Версия 1.0 — это стабильный portable-проводник, которым может пользоваться обычный пользователь Windows 11 x64.

Он должен:

- безопасно работать с файлами и папками;
- не терять данные при копировании, перемещении и удалении;
- корректно показывать ошибки;
- иметь понятный интерфейс;
- поддерживать RU/EN;
- интегрироваться в Windows на уровне контекстного меню, буфера обмена и drag-and-drop;
- поддерживать стандартную Корзину Windows;
- поддерживать защищённую корзину приложения;
- обновляться без ручной переустановки;
- быть пригодным для распространения другим пользователям.

---

## 3. Что НЕ входит в версию 1.0

Следующие функции сознательно откладываются после 1.0:

- полная замена `explorer.exe`;
- подмена рабочего стола Windows;
- собственная реализация панели задач;
- глубокие shell namespace extensions;
- COM-серверы для системной интеграции;
- поддержка Windows 10;
- поддержка Windows 7/8;
- поддержка ARM64;
- гарантия криптографического стирания данных на SSD;
- облачная синхронизация настроек;
- телеметрия по умолчанию;
- система плагинов для сторонних разработчиков;
- встроенный терминал;
- встроенный редактор кода;
- продвинутый поиск по содержимому всех файлов;
- создание и редактирование архивов, кроме базовой поддержки ZIP, если она не будет стабильной.

Полноценная замена Explorer рассматривается как отдельная версия 2.0 или экспериментальный режим после 1.0.

---

## 4. Целевая платформа

- Windows 11 x64.
- Запуск без прав администратора.
- Portable-режим.
- Настройки по умолчанию хранятся в `%LOCALAPPDATA%`.
- Опционально поддерживается portable-конфигурация рядом с `.exe`.

## 5. Рекомендуемый технологический стек

### UI

Основной выбор:

- Rust;
- `egui` / `eframe`.

Причины:

- чистый Rust без веб-слоя;
- быстрый цикл разработки;
- хорошо подходит для списков файлов, деревьев, вкладок, панелей свойств, диалогов;
- позволяет контролировать поведение на больших папках;
- можно сделать современную тёмную и светлую тему;
- проще встроить будущую Windows-интеграцию, чем в веб-решения.

Альтернатива, если потребуется более нативный вид Windows 11:

- `Slint`.

Не рекомендуется для 1.0:

- `Tauri`, потому что он добавляет WebView-слой и усложняет системную интеграцию для файлового менеджера.

### Windows API

- crate `windows`.

Через него будут реализованы:

- стандартная Корзина Windows через `IFileOperation`;
- буфер обмена в формате `CF_HDROP`;
- drag-and-drop через OLE;
- работа с реестром для контекстного меню;
- known folders;
- запуск файлов программой по умолчанию;
- single instance;
- проверка подписи для автообновления, если потребуется.

### Основные вспомогательные crates

Ориентировочно:

- `serde` и `serde_json` — настройки и метаданные;
- `tracing` и `tracing-subscriber` — логирование;
- `notify` — слежение за изменениями папок;
- `directories` — пути конфигурации и данных;
- `known-folders` — специальные папки Windows;
- `thiserror` — типизированные ошибки;
- `anyhow` — удобное propagate ошибок в верхнем слое;
- `image` — предпросмотр изображений;
- `zip` — чтение и извлечение ZIP;
- `walkdir` — рекурсивный поиск;
- `nucleo-matcher` или аналог — fuzzy-поиск;
- `fluent-bundle` и `unic-langid` — локализация, либо простой JSON-ресурс, если Fluent окажется избыточным;
- `sha2` — контрольные суммы для обновлений;
- `reqwest` — загрузка обновлений.

Конкретные версии фиксируются на этапе старта проекта, чтобы все зависимости собирались вместе стабильно.

## 6. Архитектурные принципы

Код должен быть разделён на слои.

### `core`

Независимая бизнес-логика:

- файловая система;
- операции копирования, перемещения, удаления;
- очередь задач;
- история навигации;
- закладки;
- поиск;
- защищённая корзина;
- настройки;
- ошибки;
- логирование.

`core` не должен знать про egui, Slint или Win32 API.

### `platform/windows`

Специфика Windows:

- реестр;
- контекстное меню;
- Корзина Windows;
- буфер обмена;
- drag-and-drop;
- эскизы;
- single instance;
- автообновление;
- вызов системных Shell API.

### `ui`

Интерфейс:

- вкладки;
- список файлов;
- дерево папок;
- панель свойств;
- диалоги;
- прогресс операций;
- контекстные меню внутри приложения.

UI не должен напрямую удалять, копировать или менять файлы. Он отправляет команды в `core` или `platform`.

### Почему это важно

Такая архитектура позволит:

- позже заменить UI;
- подготовить режим замены Explorer;
- тестировать файловые операции без окна;
- избежать превращения проекта в один большой файл;
- снизить риск потери данных из-за хаотичной логики.

### Правила безопасности

Для копирования:

1. Проверить источник.
2. Проверить назначение.
3. Проверить свободное место, если возможно.
4. Копировать данные.
5. Проверить успешность записи.
6. Только после успеха считать копию завершённой.

Для перемещения:

- в пределах одного тома можно использовать rename;
- между томами выполнять:
  1. copy;
  2. verify;
  3. delete source.
- никогда не удалять источник до успешного завершения копии.

Для удаления:

- если выбран режим Корзины Windows, использовать системную корзину;
- если выбран режим защищённой корзины, перемещать в controlled storage;
- для удаления навсегда требовать явное подтверждение.

### Критерий готовности

- ✅ Можно скопировать большую папку.
- ✅ UI не зависает во время операции.
- ✅ Операцию можно отменить.

### Почему этот этап критичен

Файловый менеджер теряет доверие, если один раз тихо повредит или потеряет файл. Этот этап нужно делать особенно аккуратно.

## Версия 0.5 — Базовая Windows-интеграция

## Версия 0.8 — Защищённая корзина приложения

### Цель

Реализовать отдельную надёжную корзину с восстановлением, метаданными и проверкой путей.

### Задачи

  - идентификатор тома, если возможно;
  - статус восстановления;
  - контрольную сумму, если решено использовать.
- [ ] Реализовать удаление в защищённую корзину.
- [ ] Реализовать восстановление из защищённой корзины.

- [ ] Реализовать очистку защищённой корзины.
- [ ] Показать список удалённых файлов.
- [ ] Показать, откуда был удалён файл.
- [ ] Проверять, не появился ли файл по исходному пути.
- [ ] При конфликте предлагать:
  - восстановить с новым именем;
  - перезаписать;
  - пропустить;
  - отменить.
- [ ] Защитить корзину от опасных путей:
  - относительные пути;
  - `..`;
  - symbolic links;
  - junction points;
  - mount points;
  - пути вне разрешённых корней.
- [ ] Корректно обрабатывать случай, когда исходный диск исчез.
- [ ] Добавить настройку режима удаления:
  - стандартная Корзина Windows;
  - защищённая корзина приложения;
  - спрашивать при удалении;
  - использовать защищённую корзину для отдельных папок.

### Где хранить защищённую корзину

Варианты:

1. В `%LOCALAPPDATA%`.
   - Просто.
   - Безопасно.
   - Но для больших файлов между дисками может быть медленно.

2. На том же томе, например:

   ```text
   D:\.FileManagerSecureTrash\
   ```

   - Быстро.
   - Меньше риск повредить данные.
   - Сложнее обрабатывать съёмные диски и права.

Рекомендация:

- по умолчанию пытаться использовать корзину на том же томе;
- если нельзя — использовать `%LOCALAPPDATA%`;
- дать пользователю настройку политики.

### Важно про «безопасное стирание»

Для версии 1.0 не обещать криптографическое уничтожение данных.

Корректная формулировка:

> защищённая корзина с контролируемым удалением и восстановлением

Некорректно для 1.0:

> гарантированное безопасное стирание данных на SSD

На SSD обычная перезапись не гарантирует физического уничтожения старых данных. Настоящее secure erase — отдельная сложная задача после 1.0.

### Критерий готовности

- [ ] Файл можно удалить в защищённую корзину.
- [ ] Файл можно восстановить.
- [ ] Восстановление не ломает существующий файл без спроса.
- [ ] Повреждённые метаданные не роняют приложение.
- [ ] Symbolic links не позволяют выйти за пределы корзины.
- [ ] Очистка корзины работает предсказуемо.
- [ ] Пользователь видит, что именно будет удалено навсегда.

### Почему этот этап важен

Ты хотел именно защищённую корзину. Это функция доверия. Если она работает неправильно, она может стать опаснее обычного удаления.

## 10. Главные риски и как их снижать

### Риск 1: UI будет тормозить на больших папках

Причина:

- попытка отрисовать все элементы сразу;
- синхронное чтение метаданных;
- генерация эскизов в основном потоке.

Решение:

- виртуализированный список;
- фоновая загрузка;
- ленивые эскизы;
- отмена задач для невидимых элементов;
- кэш;
- ограничение одновременных операций.

---

### Риск 2: Потеря файлов при копировании

Причина:

- удаление источника до успешной копии;
- отсутствие проверки ошибки записи;
- отсутствие журнала операций.

Решение:

- copy → verify → delete;
- временные файлы, где уместно;
- проверка свободного места;
- журнал операций;
- тесты аварийного завершения;
- запрет удаления источника до подтверждения копии.

---

### Риск 3: Заблокированные файлы ломают очередь

Причина:

- один файл удерживается другим процессом;
- операция останавливает всю очередь.

Решение:

- retry с таймаутом;
- кнопки «повторить», «пропустить», «отменить»;
- продолжение очереди после пропуска, если пользователь разрешил;
- понятное сообщение в окне ошибок.

---

### Риск 4: Контекстное меню ломает систему

Причина:

- неправильные записи реестра;
- конфликт с другими программами;
- использование `HKLM` без необходимости.

Решение:

- использовать только `HKCU`;
- уникальные ключи;
- кнопка «отключить интеграцию»;
- чистое удаление записей;
- не трогать системный Explorer.

---

### Риск 5: SmartScreen и антивирусы ругаются на `.exe`

Причина:

- неподписанный неизвестный файл;
- частая смена имени или пути;
- подозрительная активность обновления.

Решение:

- подпись кода;
- стабильные релизы;
- проверка хэшей и подписи при обновлении;
- понятный источник распространения;
- инструкция для пользователя.

---

### Риск 6: Длинные пути и спецсимволы

Причина:

- Windows API исторически плохо работает с длинными путями;
- Unicode, эмодзи, правосторонние тексты, точки в конце имени.

Решение:

- wide API;
- long path awareness в манифесте;
- поддержка префикса `\\?\`, где нужно;
- тесты с эмодзи, китайскими, арабскими, японскими именами;
- не обрезать пути вручную.

---

### Риск 7: Сетевые папки и съёмные диски

Причина:

- устройство исчезло во время операции;
- сеть недоступна;
- задержка ответа диска.

Решение:

- таймауты;
- обработка ошибок устройства;
- отмена операций;
- понятные сообщения;
- обновление списка дисков;
- не пытаться бесконечно повторять операцию.

---

### Риск 8: Защищённая корзина становится уязвимостью

Причина:

- восстановление по недоверенному пути;
- symbolic links;
- junction points;
- повреждённые метаданные.

Решение:

- хранить абсолютные пути;
- проверять том;
- запрещать выход за разрешённые корни;
- проверять symlink / junction;
- не выполнять файлы из корзины автоматически;
- показывать пользователю, что именно восстанавливается.

---

### Риск 9: Попытка сразу заменить Explorer

Причина:

- слишком сложная системная интеграция;
- высокий риск сломать пользовательскую сессию.

Решение:

- не включать замену Explorer в 1.0;
- сделать standalone-проводник;
- позже добавить экспериментальный Shell Mode;
- обязательно иметь аварийный возврат к стандартному Explorer.

## 13. Итоговое решение по стеку для 1.0

Для версии 1.0 фиксировать:

- язык: Rust;
- UI: `egui` / `eframe`;
- Windows API: crate `windows`;
- настройки: JSON через `serde`;
- логи: `tracing`;
- файловые операции: собственная очередь в `core`;
- Корзина Windows: `IFileOperation`;
- защищённая корзина: собственный слой с метаданными и проверкой путей;
- буфер обмена: `CF_HDROP`;
- drag-and-drop: OLE через Windows API;
- single instance: mutex + именованный канал или аналог;
- автообновление: отдельный updater + проверка SHA-256 и подписи;
- локализация: RU/EN;
- дистрибуция: portable + updater.

Это даёт баланс между скоростью разработки, контролем над системой и возможностью позже вырасти в полноценную замену Explorer.
